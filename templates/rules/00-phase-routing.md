# 階段路由

常駐規則，無 `paths` frontmatter。

研究工作分六個階段。每個階段有**該用的工具**與**出口條件** ——
出口條件沒滿足就不要進下一階段。

出口條件的意義不是儀式，是防止**在錯的階段修錯的東西**。例如把設計問題
留到實作階段才發現，成本是好幾週的 GPU 時間；把量測問題留到撰寫階段才
發現，成本是整批結果重跑。

| 階段 | 工具 | 出口條件 |
|---|---|---|
| **理解** | `paper-search-pro` + `paper-analyst`（包 subagent）| 摘要中 `[原文陳述]` 與 `[模型推論]` 分開 |
| **設計** | `grill-me` → 對抗型 reviewer（見下「審查」）→ `exp-design-check` | 三道走完，計畫凍結存進 `.context/plans/` |
| **實作** | worktree；有凍結檔案時加保護（見 `20-stable-core`） | 產出對得上凍結的計畫 |
| **分析** | 統計計算包 subagent，判讀由主 agent 做 | 結論標明不確定性 |
| **撰寫** | `humanizer-research-zhtw` | 通過中文用詞檢查 |
| **交接** | `handoff` + SessionStart / Stop hook | `current-focus.md` 已更新 |

## 各階段的重點

**理解** —— 完整流程：

1. **先查 `.context/papers/pdf/MANIFEST.md`** —— 已收錄的不要重複找
2. 未收錄才用 `paper-search-pro` 搜尋（搜尋與摘要可平行跑：
   `lit-scout`、`paper-digest`）
3. PDF 下載到 `.context/papers/pdf/`
4. `paper-analyst` 產出筆記到 `.context/papers/`
5. **更新 MANIFEST**：檔名、標題作者、arXiv ID 或 DOI、版本、對應筆記
6. 筆記開頭標明基於哪一份 PDF

第 1 步不是禮貌性檢查 —— 沒有它，同一篇論文會被反覆搜尋、反覆摘要，
而且兩份摘要不會一致。

**版本規則：同一篇論文有多版時，兩版都收**，並在 MANIFEST 記錄差異摘要
與「我們對齊哪一版」。**不要只留新版。** 舊版常常解釋了某份實作為什麼是
那樣（它逐字符合舊版）；沒有舊版，就會把版本落差誤判成 bug。

出口條件是標記制度：分不出哪句是論文說的、哪句是模型推的摘要，
下游引用時會把推論當事實。

**設計** —— 三道順序不能換。`grill-me` 先問出「這一輪要測什麼、什麼結果
會推翻它」，對抗型 reviewer 抓單一視角的盲點，`exp-design-check` 最後確認
「這樣跑合不合理」。計畫凍結之後才進實作。

**實作** —— 判準是**產出對得上凍結的計畫**，不是通過某個覆蓋率門檻。
偏離計畫要回到設計階段，不要在實作階段偷改目標。

**分析** —— 統計計算（檢定、檢定力、信賴區間）可以委派給 `stat-runner`；
**判讀不可以**。判讀要決定「這個數字代表什麼、要不要據此改方向」，
那是判斷。

**撰寫** —— 檢查是報告制不是改寫制，作者決定要不要採納。

**交接** —— 交接文件寫了但沒更新 `current-focus.md` 的常駐區等於白寫，
因為下一個 session 是靠 hook 注入知道現況的。

## 審查（reviewer）

審方法、審實驗設計、審論文主軸，一律用**單一對抗型 reviewer agent**。
不平行開多個角色、不臨時改用其他 review 工具代替 —— 多個聲音只會把判斷
丟回給你綜合，而一個帶著明確判準的 reviewer 才會給出可以反駁的結論。

給 reviewer 的 prompt 要有：

1. **使用者的判準當評分規則**，與既有限制（哪些做法已被排除、不能當建議）。
   判準本身記在專案的 `.context/`，不寫死在這裡。
2. **設計用中性描述** —— 不寫自己的偏好、不替方法辯護。
3. **先列推翻條件**，再評優缺點。
4. **粒度照最終產出**（論文審查就照論文會寫的粒度，不鑽到個別參數或個別樣本）。
5. 審論文主軸時以**完成品**為前提：缺實驗不是主軸問題。

文獻查證不屬於 reviewer 的工作，走上面的「理解」流程（先查 MANIFEST）。

## 通用：subagent 的界線

**subagent 只做調查、分析、摘要。需要判斷或需要停下來問的不得委派。**

技術理由：subagent 無法使用 `AskUserQuestion`，也無法在需要授權時停下來
等待。所以一件需要人工 gate 的事交給 subagent，它只會自己選一個答案
往下做，而那個選擇不會有人看到。

換句話說，「這件事需要人工 gate」和「這件事不能委派」是同一個判準的
兩種說法。**如果你會想幫使用者回答，那它就是 gate，也就不能委派。**

可以委派的：找論文、讀論文、跑統計、掃程式碼、比對檔案。
不能委派的：選哪個方案、要不要接受這個結果、判準怎麼定、要不要進下一階段。
